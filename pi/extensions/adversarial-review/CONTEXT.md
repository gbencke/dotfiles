# CONTEXT — adversarial-review

Glossary for the adversarial-review pi extension. No implementation details.

## Terms

- **Extension** — the self-contained package at `~/.pi/agent/extensions/adversarial-review/`. Bundles docs, skills, role packs, lenses, and the matrix launcher. Spawns no subagents; scale comes from parallel processes.
- **Lens** — one review domain (aws, docs, tests, chaos, test-surface, blast-radius, …). Physically a directory of markdown rule packs (`lens.md` manifest with apply-when signals, `rules.md` checklist, optional `conventions.md`) under `lenses/`. Lenses are discovered by scanning; no code, no registration. Lenses are the unit of extensibility: adding a topic = adding a directory.
- **Finding** — a single review issue. To count as a finding it must name a specific code path, a specific failure condition, and specific evidence. "Consider adding error handling" is not a finding.
- **Review** — an evidence-backed assessment of a pinned revision under declared lenses. Shapes: repo, change, and finding verification. A focused verification never issues whole-PR approval.
- **Ledger** — cumulative finding records in v2 sidecars. Stable IDs survive line/title changes; explicit aliases reconcile legacy identities. Absence never means closure.
- **Disposition** — open, fixed_verified, disproved, deferred, or not_rechecked. Fixes/disproofs require closure evidence; nonblocking deferrals need owner/ticket. Unrechecked rows retain prior_status and evidence.
- **Coverage** — invariant → entry points → all writers → final consumers → outcomes, with evidence or a concrete unresolved next check. Safety and liveness are distinct obligations.
- **INCOMPLETE** — insufficient critical evidence, snapshot drift, unrechecked active history, or unresolved high-risk uncertainty. It is not SHIP with a footnote.
- **Report validator** — extension-owned Node helper checking schema, counts, history continuity, scope, closure records, and read-only Git/patch snapshot consistency. It cannot prove evidence is semantically correct.
- **Adversarial loop** — the fixed pipeline every review runs: **Propose → Kill → Judge**. Three phases in one process, in order: the reviewer role proposes findings, the challenger role tries to kill each one, the judge role dedups, assigns severity, and delivers the verdict. Phase separation is the point; process separation is not (ADR 0004).
- **Role pack** — one of `agents/reviewer.md`, `agents/challenger.md`, `agents/judge.md`: the stance, contract, and output schema for one phase. The reviewing process reads them and adopts one at a time. Not subagent prompts, not pi agent types.
- **Matrix run** — one review per (repo × lens), every pairing launched as its own `pi -p` process at the same time by `bin/run-matrix.sh`. Leaves `manifest.tsv` (repo, lens, exit, seconds, report, log) behind, so a failed lens is visible instead of missing.
- **Consolidated document** — the single cross-repo deliverable written by `/review-consolidate` to its required `--out` path: severity first, repo second, with a summary table (repo × lens × counts), a coverage table from the manifest, cross-repo themes, and a `## Not consolidated` section. Lives outside the reviewed repos.
- **`REPORT: ` line** — the last line of a review's chat summary: the absolute artifact path. The contract batch callers parse (`CONSOLIDATED: ` for the consolidated document), instead of guessing the newest file in a shared reports directory.
- **Challenger** — the adversarial counterpart to a lens reviewer. Tries to disprove each proposed finding by checking it against the actual code. Verdicts: **VALID** (real, survives), **INVALID** (disproven, dropped), **AMBIGUOUS** (needs human judgment, reported with lower confidence).
- **Judge** — the final arbiter across all lenses. Deduplicates surviving findings, assigns severity (P0–P3), and issues the review verdict. Never reviews code itself; rules only on challenger-verified input.
- **Project lens overlay** — a `.gbencke/adversarial-review/lenses/` directory in the reviewed repo, same format as global lenses. Same-named lenses merge (project rules append after global); new names add repo-only lenses.
- **Chaos lens** — static resilience review (timeouts, retries/backoff, circuit breakers, idempotency, graceful degradation, cleanup) plus *proposed* chaos experiments (steady-state hypothesis + fault + expected behavior). Never executes anything; no manifests, no live calls.
- **tests lens** — coverage gaps and test quality. Reads existing coverage reports (coverage.xml, lcov.info) when present; otherwise statically maps code files to test files. Never runs the test suite.
- **test-surface lens** — for a change: enumerates the behavior surface (touched public APIs, new branches, error paths) and checks each element has a test that would actually fail if it broke. Change reviews only.
- **blast-radius lens** — for a change: reverse-dependency impact — who imports/calls the changed symbols, what breaks downstream, risk tier.
- **aws lens** — static review of IaC (Terraform/CDK/CloudFormation) and AWS-SDK code against Well-Architected pillars and documented service quotas/limits. No AWS credentials, no live API calls.
- **Execution boundary** — reviews never execute repo code, tests, builds, or live services. Read-only Git/PR/JIRA metadata, exact-head CI logs, and extension-owned data helpers are allowed. Matrix pi subprocesses are reviewers, not application execution.
- **Repo review scoping** — exhaustive: every source file is reviewed, chunked along module/directory boundaries (oversize directories split mechanically by token budget). Generated, vendored, and lock files are always skipped. Cross-chunk duplicate findings are the Judge's problem, not the user's.
- **Change review scoping** — the diff is the scope; all lenses apply (including the change-only test-surface and blast-radius lenses). Blast radius = mechanical reverse import/caller graph (ast-grep, grep fallback) plus an agent semantic pass for couplings imports can't see (events, queues, HTTP contracts, DB schemas).
- **Dual verdict** — full change reviews assess implementation and solution fit, subject to coverage/closure gates. Repo reviews have per-lens health plus a scoped summary. Finding-verification verdict fields are null; only named issue dispositions are reported.
- **Report** — Markdown plus a schema-v2 sidecar in the reports directory. UTC timestamps, revision/scope metadata, cumulative ledger, coverage, and separate confirmed/uncertain counts are required. CLI, final-message, and matrix validation guard publication; see docs/report-contract.md.
- **v1 lenses** — aws, design, docs, tests, chaos, test-surface, blast-radius, security, performance, error-handling, typescript, golang, python.
- **Language lens** — a lens whose signals are file globs (`*.go`, `*.ts`). Language lenses review only the chunks (repo review) or diff files (change review) that match their language; other lenses (`always`) review everything.
- **Lens selection** — automatic and silent: every lens whose signals match runs. `--lenses a,b,c` narrows it, and one lens per run is the matrix case. There is no lens picker and no prompt — a prompt would deadlock the non-interactive `pi -p` processes a matrix run is made of.
- **design lens** — reviews code against the structural chapters of Ousterhout's *A Philosophy of Software Design* (complexity, deep modules, information hiding, abstraction layers, names, obvious code). Error-handling (ch10) and comments (ch12–13) belong to their own lenses and are excluded to avoid double-reporting.
- **Blast radius** — the set of code, tests, and downstream consumers affected by a change.
